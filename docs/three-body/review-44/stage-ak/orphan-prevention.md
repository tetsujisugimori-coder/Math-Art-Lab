# P2-AK02 OPEN: preassignment ownership and native candidate

Baseline CREATE_SUSPENDED -> AssignProcessToJobObject -> IsProcessInJob -> ResumeThread leaves a child outside J between creation and assignment. A creator crash, hang or communication loss can strand that suspended child. KILL_ON_JOB_CLOSE cannot protect a process not yet assigned. A parent-process anchor proposal merely moves the problem to creating the first anchor. No such process is created here.

Preferred design candidate for later implementation: M itself as a native monitor EXE containing C/D/E logical units in the same process, using CreateProcessW + STARTUPINFOEXW + EXTENDED_STARTUPINFO_PRESENT + PROC_THREAD_ATTRIBUTE_JOB_LIST, also CREATE_SUSPENDED, followed by IsProcessInJob and retained-handle/creation-identity verification before ResumeThread. The job list must be ordered to satisfy nested hierarchy. It differs from a postcreation AssignProcessToJobObject fallback; inability to use the reviewed creation-time path means refusal, not silent fallback/resume. This is a selected **candidate API interface**, not an implemented binary or a proof of all kernel failure outcomes.

| Transition/fault | Planned owner and evidence | Safe-side result |
|---|---|---|
| before creation | M owns noninherited J handle; R enrolled VM and session first | missing R/VM/rights => NO launch |
| creation returned suspended | M retains actual process/thread handles, native creation time, job membership and session capability | no PID lookup as authority |
| creator loss during API | R independent VM-level recovery and external ledger | outcome/membership may be NOT_OBTAINED; no complete rollback assumed |
| assignment/job-list/nested/ACL failure | native return/error bytes, any obtained handles; exact process incarnation only | never resume uncontained; prove cleanup or remain UNCONFIRMED/BLOCKED |
| membership verified | native IsProcessInJob and expected retained handle/creation identity, parent relation | absence/mismatch blocks resume |
| resume | separately recorded native result | success not equivalent to normal body completion |
| stop | native request outcome, independent handle wait/exit fact | send/ACK not EXIT |
| release | process/thread/job handle closure and owner ledger | not inferred from process exit or persistence |

Job handle owner M stays outside J; no child inherits the job handle. Explicit handle allowlist is limited to authenticated IPC capabilities; not a wholesale inherit flag. Handle leaks/duplicated last handles can invalidate conditional death behavior. Exact JOB_OBJECT_ASSIGN_PROCESS/TERMINATE/query and process SET_QUOTA/TERMINATE/query/synchronization/thread-resume rights must be checked against each chosen API and actual ACL; no ALL_ACCESS default or elevation is approved. Creation-time job-list rights and failure/partial-rollback details require native verification; documentation is not a universal creator-death atomicity guarantee. Existing parent Job/UI/security restrictions may reject a hierarchy. Breakaway and unrelated process actions forbidden.

API-reference retrieval for UpdateProcThreadAttribute timed out in this pass; search excerpt and article support candidate selection, with exact flags/rights still a required implementation review. No Q&A answer or sample lacking error checks is treated as proof.

Closure requires actual native version/ACL/hierarchy, birth/handle enrollment before resume, bounded independent recovery for creator loss (including before API return), no foreign target action, separate exit/release/receipt facts and independently authorized physical qualification. All remain NOT_TESTED; AK02 stays OPEN.

C/D/E share the M process and one native handle-ownership ledger; there is no second helper process requiring a duplicated job capability. Their reserved .cc paths are specifications only and do not exist. Node P/W communicate over separately authenticated bounded IPC. Only allowlisted IPC handles can be inherited: when PROC_THREAD_ATTRIBUTE_HANDLE_LIST is used, those handles must be inheritable and CreateProcess bInheritHandles=TRUE; the Job handle remains non-inheritable and absent from that list. Passing it in JOB_LIST is assignment metadata, not child ownership. Verify every native handle and last-close condition before claiming death containment.
