# Host facts versus unobtained isolated VM

current-host-windows.json is a read-only registry receipt from the development host: edition Core, ProductName Windows10 Home, build26300, UBR9974, DisplayVersion26H2, architectureX64. ProductName is preserved as reported, not corrected/inferred into a qualified OS marketing name. This host is not the disposable experiment VM. No VM was started, enumerated through management tools, configured or stopped.

safety-contract.json.vm explicitly retains20 unobtained fields: OS edition/build/UBR/architecture, image/hash/origin, VM UUID/generation/hypervisor, operator/administrator/recovery owner, account/ACL/job hierarchy/ownership receipt, external console/management rights and restoration evidence boundary. No identity or permission is guessed from the current user. Future admission requires original VM image bytes/hash/source, immutable guest and hypervisor identities, least-privilege account/ACL receipt, job ancestors/restrictions, communication boundary and independent recovery owner. Host/guest management credentials must not be included in published ledgers.

node-dependencies.json pins actual current Node executable path/size/SHA, ABI/N-API, Vitest/Vite metadata, package-lock raw hash and full package dependency/optional/engine graph. Installed metadata is current static evidence, not historical measurement or VM compatibility. toolchain-candidates.json inventories only selected existing compiler executables and Windows SDK headers by path/size/raw SHA. Compiler binaries were not invoked, addons/DLLs not loaded, signatures/runtime dependencies not verified. Other installation locations were not exhaustively searched. No arbitrary candidate is promoted to selected toolchain.

Future bridge candidate is a standalone x64 native monitor EXE (M itself; C/D/E logical units in one process), reducing in-process addon/DLL loading into the Vitest worker. No binary exists; source/commit/hash, binary/hash, signature and ABI compatibility remain null/UNKNOWN/NOT_OBTAINED. If later design chooses an addon instead, require explicit Node module ABI/N-API contract and loader isolation review; do not substitute it silently. A helper still needs its compiler, SDK import libraries, runtime DLL set and IPC protocol pinned. Library search must use approved absolute deployment paths; no PATH/current-directory loading of unpinned DLLs. No such loader is implemented here.

Build receipt requirements: source commit/tree/blob/SHA and generated inputs; exact compiler/linker/SDK/runtime files with size/hash/signature status; flags, defines, target x64 and reproducible build environment; dependency graph/lock; output EXE/DLL/addon raw bytes/size/SHA, signing identity and verification result, ABI descriptor and source-to-binary attestation. Unknown signature is not VALID. Missing output means no output SHA is fabricated. Independent rehash and architecture/ABI/load-boundary verification precede any separately approved qualification; none is performed now.

No separately spawned native helper owns a duplicate job capability in this candidate. C/D/E .cc paths are reserved only; original AJ planned paths remain untouched as historical proposals. A change to a separate helper process would require a new reviewed handle-transfer/last-close contract.
