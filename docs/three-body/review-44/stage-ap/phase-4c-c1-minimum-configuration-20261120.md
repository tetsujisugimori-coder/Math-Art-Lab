## 1. 役割・候補・固定範囲

| 役割 | 第4工程Cで選ぶ第一候補 | 明確に未固定な事項 |
|---|---|---|
| H（VMホスト） | **将来購入する新デスクトップ**、Windows 11 Pro + クライアントHyper-V | 具体的機種、実CPU/UEFI仮想化機能、メモリ・SSD、OS/guestライセンス、ネットワーク、設定・配備・稼働 |
| G（停止対象） | H上の**使い捨てWindows VM 1台**。VM ID・image SHA・generation/epoch・sessionに結び付ける | guest OSの実行権、実VM ID、イメージ、生成方法、Job/handle実証 |
| R（外部停止） | **現行ギャラリア**。H/Gとは別物理PC、対象Gの状態readと単発STOP要求を担う候補 | 管理先への到達性、制限権限、鍵/信頼・失効、実際のSTOP能力、稼働時の給電・電源設定 |
| O（R不在でも使える別経路の観測） | **Hのローカルコンソールからの読み取り専用VM状態表示／H側ローカル記録**を第一候補にする。所有者がHへ直接アクセスする経路を想定し、RのOS・プロセス・回線・電源を使わない | H側コンソールの実物・アクセス方法、時刻/世代/相関IDの鮮度、H停止時の観測、物理的に独立した停止確認 |
| C（開始許可の論理機能） | H側でGの起動・試験枠を許可する前に、R稼働と必須の観測・登録・台帳条件を確認する設計候補 | 実装場所、故障時の拒否の実効性、H自体が停止した場合の進行中枠 |
| HUMAN | 所有者によるH現地コンソール確認・手動緊急対応の候補 | 操作手順、現地到達性、対応時間。自動90秒保証には算入しない |

**独立性の限定：** OはR故障に対する「別の読み取り経路」であり、H側管理サービス・電源・OSと故障領域を共有する。Oから見えるHyper-V管理状態を「独立物理センサーによるVM停止確認」に格上げしない。Hが停止・ハングすればOも利用不能の可能性がある。第3の物理PC購入は**この設計段階では必要条件としない**が、H故障時の独立観測・停止を保証する代替策が成立した意味でもない。

## 2. 最小構成図と通信・管理経路（全経路未実装）

```text
                      所有者（手動、90秒保証の外）
                                   |
                    O: Hローカルコンソール／記録
                       （Rに非依存、Hには依存）
                                   |
+--------------------------- H: 新デスクトップ ------------------------+
| Windows 11 Pro + Hyper-V（候補／未購入）                           |
|                                                                       |
|  C: 試験枠開始許可の論理機能  ->  G: 対象Windows VM 1台（未作成）     |
|  管理側: 対象VM限定のread/status/STOP endpoint（方式未選定）           |
|  台帳: rollback対象外の登録・nonce永続記録（場所・権限未選定）        |
+-----------------------------^-----------------------------------------+
                              | M1: R→Hの限定管理経路
                              | VM同定・認証・状態read・単発STOP
                              |（実LAN/endpoint/ACLは未構築）
+-----------------------------+-----------------------------------------+
| R: 現行ギャラリア（Windows Home系、別物理PC）                       |
| R自身の稼働確認、対象VM限定STOP送信の候補（まだ動作しない）            |
+-----------------------------------------------------------------------+

※ R/G両方に依存しない開始許可の設計条件をCに要求する。
※ OはR障害時の別経路候補。H障害時の代替センサーではない。
※ 外部原票保存先・R/H共通電源・管理LAN・認証基盤は未固定。
```

| 経路 | 送信元→宛先 | 許すべき操作・境界 | 現状 |
|---|---|---|---|
| M1 管理 | R→Hの制限endpoint→対象G | 特定VM ID／generation／epochに限るread・認可されたSTOP。任意PowerShell・別VM操作・H全体管理は禁止。ゲスト内IPCには依存しない | `NOT_PROVISIONED`。JEA等は候補であり実現性と権限分離は未検証 |
| O1 別読取 | 所有者→Hの現地コンソール／Hローカル記録→対象Gの状態 | Rなしで照会できること。VM ID、世代、操作相関、観測時刻・情報源の鮮度を別途確認 | `DESIGN_CANDIDATE`。管理側と同じ状態源なら物理的独立性なし |
| C1 開始許可 | C→G起動／試験開始の制御 | 新規枠ごとにR稼働・必要O・登録台帳・有効な許可を確認。確認できない場合は開始拒否 | `DESIGN_ONLY`、無停止保証・実装なし |
| E 証拠 | H/Rで取得した原票→承認済みguest rollback外保管先 | 観測と保存・読戻しは独立判定。Rにしか証拠がない構成はR障害に弱い | 保存先・実読戻し・アクセス権未確定 |

**STOP状態の区別：** `STOP_REQUESTED`、`MANAGEMENT_ACCEPTED`、`MANAGEMENT_OPERATION_RESULT`、`VM_STOPPED`、`GUEST_PROCESS_EXIT`、`RESOURCES_RELEASED`、`EVIDENCE_SAVED/READBACK`を独立判定する。管理側の操作成功やローカルコンソールでの状態表示だけでは、別の物理センサーによる実停止、guest process exit、資源解放を証明しない。未検証のため `VM_STOPPED` 実証は `NOT_TESTED` のまま。

**送信前後契約：** 対象VM・image・generation・epoch・sessionへの認証済み登録と、guest rollback外のnonce消費の永続commit／読戻しが確認できなければ**初回STOPも送らない**。送信後に受付・操作結果が不明なら**再送しない**。読み取り専用の確認とUNKNOWN記録のみ。今回はSTOP送信自体を実施しない。

## 3. 故障境界と安全側の扱い（設計契約、未実証）

| 故障・欠測 | C1の想定影響 | 許可・記録・残る限界 |
|---|---|---|
| Rがスリープ・停止・通信不可 | M1による外部STOP不可。ギャラリアはAC給電でもスリープ120分・休止121分設定（11/20実機報告） | Rの新鮮な稼働確認がなければ**新規枠開始禁止**。既に進行中の枠の停止は保証なし、未確認`UNKNOWN` |
| HのOS・hypervisor・管理APIハング | M1もO1も応答不能の可能性 | H側APIへの単発要求では停止を保証できない。BMC/別系統電源制御は将来候補であり搭載・影響範囲・許可未確認。`RECOVERY_GUARANTEE=NONE` |
| Gのprocess/guestハング | ホスト管理面が動けばM1の停止候補を検討可能 | STOP受付・管理結果・VM停止・process終了を別判定。STOP実測なし |
| R/H共通停電・同一ルータ障害 | 別PCでも共倒れし得る。O1はH電源・管理面と故障を共有 | UPS・別回線・給電独立性未定。新規枠の開始条件が確認不能なら開始しない。進行中はUNKNOWN |
| Oの不達・古い状態・対象誤認 | STOPの実際の結果を証明できない | 失効/世代不一致/相関不能はUNKNOWN。キャッシュや管理受付を実停止とみなさず再STOPしない |
| 認証・ACL・nonce台帳の不確定 | 誤VM停止・重複STOPの危険 | 未登録、権限不明、nonce永続化・読戻し不成立は操作拒否。一般管理者権限をRへ付与しない |
| 証拠保存・独立読戻し不能 | 証明と事後判定が欠落 | 取得済み原票を保持、欠測は`INCOMPLETE/UNKNOWN`。保存待ちによる無期限停止を行わない |
| C自身が応答しない | 新規許可を発行できない | 有効な許可がない枠は開始できない設計。期限付き許可・強制拒否は将来実証が必要 |
| HUMANが不在・現地コンソールへ到達不能 | O1の手動観測も困難 | 手動対応を自動回復・90秒上限の成立証拠に数えない |

**STOP方式を混同しない：** guestプロセス終了、guest正常shutdown、Hyper-V管理面のVM停止、H全体の電源断はそれぞれ異なる。H電源断は他VM・開発作業も巻き込み得るので、現時点で既定方式としない。
