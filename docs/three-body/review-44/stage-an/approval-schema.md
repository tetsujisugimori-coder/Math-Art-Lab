# Proposed real approval envelope

The current module accepts synthetic verdicts only and produces no permission. Real approval requires a separate reviewed implementation and a published trust policy. The proposed v1 grant fields correspond to grantFields in the pure contract. Immutable repository ID is decimal text, repository full name and PR are exact, branch is an exact full ref. A different branch policy requires a reviewed revision of the schema. Also sign action and policy version, HEAD/tree, source/plan/environment/scope digests, VM UUID and generation/epoch, exact path list and permission, owner ID and role, issuer/key IDs, grant ID, nonce, status lookup ID, and issuance/expiry UTC epoch milliseconds.

The signed message is protocol-domain ASCII prefix Math-Art-Lab/Stage-AN/grant/v1 followed by one NUL and the canonical UTF-8 payload. Canonical profile uses RFC 8785 on this restricted flat schema. ASCII strings, sorted unique exact repo-relative paths, no floats or out-of-range integers, no unknown/duplicate fields, no BOM or invalid UTF-8. Parse under byte/shape limits, re-encode and compare original bytes before checking the signature. Preserve and hash original payload and envelope separately. No normalization of string values, path case or separators. Future scope validation checks a fixed allowlist and disallows reparse points, aliasing and path substitution in the working tree.

Ed25519 (RFC 8032) is the sole v1 candidate, subject to owner and independent platform review. The envelope carries a detached 64-byte signature with a strict fixed encoding. Pin the issuer, algorithm, public key fingerprint, owner authority for exact repository/action, key validity and status service outside the message. Reject unknown or disabled keys and algorithm downgrade. Store future private keys in separately authorized protected signing infrastructure. Rotation preserves audit history with effective times and explicit revocation. AN uses no keys, signatures, credentials or online authentication.

Acquire original envelope and signed status independently through approved sources. Preserve raw bytes, source identity, timestamp, request/context and response digests. Verify authenticity against pinned trust and require fresh authenticated revocation evidence for both grant and signing key. Require independent trusted UTC bounds with defined uncertainty, strict expiry and freshness policy. Unavailable trust, timestamp, revocation or conflicting readback fails closed. Revalidate at the point of use, with the authorization and revocation consistency model independently reviewed before activation.

Before any future use, atomically reserve both issuer/owner/nonce and issuer/grant ID in a durable external ledger whose generation cannot be rolled back with the guest. A losing concurrent writer, duplicate under another epoch, uncertain result, replay or save failure refuses admission. Persist context digest, decision and version, verify independently read-back original bytes and predecessor/monotonic ledger state. Use an atomic create-if-absent transaction, never a check/write pair or blind retry. A reservation consumed before a later failure stays consumed. The synthetic ledger receipts only check modeled obligations and do not exercise transaction semantics.

Model sequence PLAN_ONLY → SPEC_FROZEN → REVIEW_ACCEPTED → OWNER_REQUEST_READY. The next edge IMPLEMENT_ONLY requires a validated owner grant against independently loaded context. Only a separately reviewed actual implementation and completed safety prerequisites can reach QUALIFICATION_REVIEWED. QUALIFICATION_RUN requires a second, distinct action grant. Any error, status loss, revoked key, environment drift, rollback or expired grant blocks the campaign. Late success does not clear failures. Current pure transition checks edges only and cannot enter the external states. No experimental action is authorized.

Sources [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) and [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032).
