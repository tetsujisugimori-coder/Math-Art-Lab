## 設計と数学

各画素の中心をx,y=−6〜6に対応させ、yの正は画面の上。Pの値は選択座標を直接評価し、画像の画素値と混同しない。発生源は(−d/2,0)、(d/2,0)。位相差は `k(r_B−r_A)+φ`、Bは `2|cos(Δ/2)|`。入力の度からラジアンへの変換は `radians` に集約。描画時間は実時間差に速度を掛け、1ステップはT/40=0.05。設定適用・プリセット・時間リセットは停止する。教材開始時の状態を退避し、終了時に戻す。

Canvas 2Dを選んだのは倍精度の計算を観察値と照合しやすく、依存やGPU実装を増やさずに済むため。240×240画素固定、DPRを描画解像度に反映せず、距離位相と包絡振幅は設定変更時に事前計算する。Bは時間更新では再描画しない。同期計算なので古い非同期結果は存在しない。タブ非表示時はループを止め、復帰時の時間差を捨てる。切替時はループ、イベント、バッファを解放する。

手計算：初期P=(0,0)でr_A=r_B=2、t=0なら各波1、u=2、B=2。t=0.5ではu≈0だがB=2。独立したPython `math.dist` と三角関数で、P=(1.25,−0.75)、d=3、λ=2.5、φ=60°、t=0.4の基準値 r_A=2.850438562747845、r_B=0.7905694150420949、u_A=0.9301816783486547、u_B=−0.20521347178432328、Δ=−4.129818274234324、B=0.9485015305345281 を算出し、単体テストで比較した。許容誤差1e−12はこの範囲の倍精度丸めより十分大きく、表示丸めより十分小さい。

## 観測と制約

Windows、Node 24.20.0、Intel64 Family 6 Model 183、既定条件の240²画素、事前計算後の `pixels` を10回ウォームアップし100回実行：275.3ms、平均約2.75ms。PlaywrightのNodeプロセスでの処理時間であり、ブラウザ全体のフレーム時間やFPSではない。実機iPhone Safari、スクリーンリーダー、低性能端末、電池・熱・長時間負荷は未検証。Windows WebKitは実機iPhone Safariではない。解像度は固定なので拡大時に画素近似が見える。

画像は `a.png`, `b.png`, `u.png`, `envelope.png`, `mobile.png`。初回E2Eはサンドボックス内の親ディレクトリアクセス拒否で起動できず、許可済みの権限で再実行。初回の波E2Eはreduced-motionをテスト側で明示しなかったため再生中のステップを待ってタイムアウトし、明示した後に開発Chromium/WebKitで通過した。設定切替イベントを続けて即時発行したテストは配信前に次の変更が来て失敗したため、間隔を設けて再検証した。全開発回帰は177件通過・2件スキップ・既存双子テスト1件が描画待ちでタイムアウトし、その1件は単独再実行で通過した。全本番回帰の初回は60件通過・上記のイベントテスト2件失敗。ビルドには既存の大きなバンドル警告がある。

修正後の本番ビルド全回帰はChromiumとWindows WebKitの計62件が通過した。文字200%はルート文字サイズを変えたブラウザテストで、端末の全ての拡大方法を代表するものではない。

追加したタッチテストの初回は、画面上のタッチ座標がブラウザで画素単位に丸められP=(3,2.9798)となったため、厳密な文字列一致に失敗した。表示幅と座標変換に応じた0.05座標単位の許容差で確認する。
