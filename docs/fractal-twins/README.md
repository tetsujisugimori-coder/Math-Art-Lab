# フラクタルの双子：数学・描画・検証の記録

Issue原本: [#18](https://github.com/tetsujisugimori-coder/Math-Art-Lab/issues/18)。実装は `src/twins.ts`（数学・座標）、`twins-render.ts`（中断可能な画素計算）、`twins-worker.ts`（Worker境界）、`twins-view.ts` と `twins.css`（状態・操作・教材・表示）へ分離した。

## 発散半径と有限反復

`z'=z²+c`、`r=|z|` とすると、逆三角不等式から `|z'|≥r²−|c|`。

- Mandelbrotではz(0)=0。|c|≤2のときr>2ならr²−|c|>rで、その差はrの増加とともに増える。|c|>2ならz(1)=c、r(1)=|c|>2で、以後r≥|c|を保ち `r²−|c|≥r(r−1)>r`。したがってR=2を厳密に超えたら発散する。
- Juliaではcに応じ `R=max(2,|c|+1)`。r>Rならr²−|c|>rで、増分は正で増大するため有界にとどまらない。これは十分条件で、最小半径を主張しない。
- 比較は `>` であり `≥` ではない。c=−2の0→−2→2→2を誤って発散としない。Juliaでc=−2.8125、z(0)=2.25なら2.25²−2.8125=2.25という厳密な固定点がある。常にR=2では誤判定するが、採用半径3.8125では超過しない。
- n=0からNまで調べ、Nで初めて閾値を超えた場合も検出する。結果−1は「Nまで未観測」の実装記号で、内部／所属の証明ではない。浮動小数点による判定が数学的厳密計算であるとは主張しない。

Julia側は充填集合Kcとその境界の有限反復近似を表示する。JcはKcの境界。c=0なら絶対値が毎回二乗されるので、|z(0)|<1は0へ、=1は単位円上、>1は発散する。画面の暗い円板と数学的な境界の円を区別する。参考: [Cornell Math Explorers' Club, Complex dynamical systems](https://pi.math.cornell.edu/~lipa/mec/lesson5.html)。

## 独立基準と座標

`python tools/twins-reference.py` は製品コードを読み込まずPython組込みcomplexで計算する。N=500、Juliaのz(0)=0.2+0.1i、製品と同じ発散条件で得た基準:

| c | Mandelbrotの初回超過n | Juliaの初回超過n |
|---|---:|---:|
| −0.75+0.1i | 33 | 28 |
| 0.3+0.5i | 未観測 | 未観測 |
| −0.8+0.156i | 252 | 53 |
| 0.285+0.01i | 19 | 32 |

これらは有限回・代表条件の照合であり、境界全点の厳密分類ではない。ほかに手計算で複素数加算／乗算、3+4iの絶対値5、c=0固定点、c=−1周期、c=1の0→1→2→5を検証する。

CSS表示幅W、高さH、水平複素数幅s、中心(a,b)に対し、正規化座標(u,v)は `Re=a+(u−1/2)s`、`Im=b+(1/2−v)s/(W/H)`。画素中心を用い、DPRで計算上の表示領域を変えない。DOMRectの小数付き寸法を座標変換と描画要求で共有する。整数clientHeightを使うとCSS小数寸法によりホイール基準点がずれる不具合をE2Eで検出し修正した。

単体テストは座標の手計算、逆変換、基準点を保つズーム、移動の往復、DPR差、CSS小数寸法、上限100万倍の隣接画素の区別も検証する。数値入力の1e−324など、binary64で0になる非ゼロ候補は拒否する。表示は有効数字10桁に丸めた約値で、真の0／−0は0、表現可能な微小値は指数表記を含めて保持する。

## 描画方式・資源制約

Canvas 2D＋CPU Web Workerを採用した。同期Canvas計算はUIスレッドを占有し、WebGL2シェーダーは通常のfloat精度とCPU基準の差を新たに扱う必要がある。今回の有限解像度ではCPUのbinary64計算をそのまま分離できる方式を選んだ。GPU方式の性能ベンチマークを行ったという意味ではない。依存追加なし。

各図にWorker1つ。各Workerは現在の要求と最大1つの予約コールバックを持ち、約8msを目安に行間でyieldする（1行の実行時間まで厳密な8ms上限を保証しない）。新要求で現在のジョブを置換し、未完了の画素は公開しない。UI側も世代番号で古い完了通知・取消後・dispose後の通知を拒否する。RGBA配列は最大640×640×4=1,638,400bytes（1.5625MiB）／枚。転送・ImageData・canvas・GCを含むプロセス全体のメモリは未計測。

画質より操作への応答を優先し、DPR1.5・辺640・N500で計算量を制限する。計算中は以前の画像を消して条件との混同を防ぐ。新しい条件の全画素が完成してから確定表示する。自動アニメーション／補間で数学的な値を変えない。

## 性能の観測条件

2026-10-26、Windows 11（build 26300）、Intel Core i7-14650HX・24論理CPU・16GiB RAM、Node 24.20.0、Playwright 1.58.2、headless Chromium 145／Windows WebKit、workers=1。既存テスト後の開発モード、viewport1280px・DPR1、各図510×407画素、既定範囲で各条件1回を観測した。以下は分布や性能上限ではない。

| 条件 | Chromium M / J | WebKit M / J |
|---|---|---|
| 初期c=−0.8+0.156i、N=200：Worker計算経過 | 21.7 / 15.9ms | 28 / 19ms |
| 同条件：要求→UI確定 | 44.7 / 39.9ms | 84 / 62ms |
| 12連続要求の最終c=0、N=500：Worker計算経過 | 40.2 / 92.8ms | 46 / 80ms |
| 同条件：最終要求→UI確定 | 41 / 99ms | 48 / 89ms |

Worker計算経過は最初の配列確保から完了までの壁時計時間で、yield待ちを含み、CPU占有時間ではない。UI確定には転送と描画処理を含む。連続要求中に10msタイマーがChromium21回／WebKit13回進んだことを確認したが、全フレームの応答遅延やFPSを保証する試験ではない。条件・範囲・端末によって変動する。N500は最大反復設定だが、このcと範囲が最悪負荷であるとは主張しない。
